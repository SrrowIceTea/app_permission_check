# A1 残留：插桩下应用被打死（2026-10-19 复核与后果修复）

> 一句话：**A1 没有"已修"**。2026-10-16 的 bridge 补丁 + 单 agent 只是把概率降下来，
> 10-19 现场仍反复复现（当天记录 7 次，含夹具与真实样本，最近一次 11:57:51
> `uptime 44s`）。本轮拿到了完整墓碑，崩溃点不在"执行被替换的方法"，而在
> **JIT 编译线程编译某个方法时读到无效的 dex/ArtMethod**（真实样本上另有一型崩在
> `binder:*`，同一类 ArtMethod/dex 不自洽的落点）。
> 崩溃本身属 frida-java-bridge × ART 的上游缺陷，本仓无法根治；本轮把**被打死的后果**
> （窗口静默截断、假通过、死因误归属、无重启续采）逐条修掉——注意是"后果"，
> 而且 §3.6 / §3.7 列了复核后**仍然没兜住**的 4 项。第 1 项（钩子比窗口早结束
> ~9s，即 `observed_s` ≈ "进程存活"而非"钩子在采"）是读本报告时必须记住的前提。

## 3. 本轮修掉的"被打死遗留问题"

### 3.1 窗口被截断却照常判通过 → 分段采集 + 覆盖率账本

- 新增 `mobile/tools/coverage_window.py`：把每段的"存活/死亡 + 墓碑自报 uptime"换算成
  `observed_s`（有效观测）、`truncated`、`first_death_at_s`、`caveat`。
- `device_run_thirdparty.py`：窗口改为**分段**跑（`--segment-chunk`，默认 10s）。
  每段结束查 `/proc/<pid>`：死了就①立刻取证（赶在墓碑被挤掉之前）②重启应用、重新挂钩
  ③用剩余时间继续采（`--max-restarts` 默认 2，`--min-segment-seconds` 默认 15）。
  UI 轮次用完后**窗口继续开着**（5s 粒度判活），否则"轮次跑完就收工"会让死亡发生在
  收尾之后，既看不见也来不及重启（冒烟实测：27s 死亡，6 轮 UI 在 20s 用完）。
  每段落 `app-death-segN.json`，汇总落 `app-death.json` + `coverage.json`，
  并写进 `verification.json.coverage`（含 `caveat`）+ `degraded` 标志。
- 证据包/报告：`bundle.gaps` 增加 `[orch]【采集窗口被截断】…`，PDF 报告里能看到
  "这条阴性结论只覆盖前 N 秒"。

### 3.2 死因被邻居冒名（实测错误）

旧写法"锚我们的 `Cmdline` → 向前找最近的 `*** *** ***` 头 → 向后扫 300 行"，
在**我们的墓碑头已被挤掉**时会读到上一条（UWB HAL）的 Abort message。10-19 现场
`app-death.json` 的 `cause` 就被写成 `failed to open the serial device`。

- `parse_app_death` 改为**按记录切块**（`*** *** ***` 头或 `Cmdline:` 都是边界），
  `Cmdline` 不是本包名的记录**整条丢弃**；不再有跨记录扫描。
- **按 pid 限定**：`logcat -d` 是整个环形缓冲，里面有上一轮/别的样本的崩溃。冒烟实测：
  段 0 被 `force-stop` 后，旧实现报出的是 5 分钟前另一轮的 `SIGSEGV + uptime 29s`。
  现在 `app_death_reason(package, pid=…, since_ms=…)` 只认 `pid <pid> (` / `pid: <pid>,`，
  并丢弃早于本段开始时刻的墓碑；设备目录兜底同样按 pid 过滤。
- 新增结构化字段：`signal` / `fault_addr` / `thread` / `uptime_s` / `death_ts` /
  `tombstone_seen` / `tombstone_complete`。
- `app_death_reason(package, dump_dir=…)`：logcat 里墓碑不完整时，去
  `/data/tombstones` 找**最近一份点名我们的**墓碑兜底，并把原文落 `tombstone.txt`。
- `pid_alive(pid)` 统一"同一个进程还活着"的判据（`pidof` 会被自动重启骗过）。
- `orchestrator_notes(death, package)`：原先**无条件**把 domivega 样本的四条结论
  写进所有样本的报告（"本样本的天气客户端是 loopj…"），已按包名收敛；死亡说明改为
  按本次墓碑的数据生成，不再沿用固定说法。

### 3.3 自检"进程死了也算通过" → 三态

- `fixture_selftest` 返回 `status`：`passed` / `degraded` / `failed`。
  **有事件但进程死亡 = degraded**（`passed=False`）：阳性对照成立（钩子能采），
  但 A1 原验收判据（≥1 真实事件 **且** 进程存活）不成立。
- `batch_thirdparty`：degraded 默认放行但整批标注 `selftest_degraded` +
  `coverage_caveats`；加 `--strict-selftest` 可拒绝出批。
- `batch_dynamic` 把样本级 `coverage` 摘进批次汇总，批次层面也能看出哪条被截断。

### 3.5 顺手把值哈希搬出钩子体（纯 JS SHA-256）

`values.js` 原先每次命中要 `MessageDigest.getInstance` + `new java.lang.String(bytes)`
+ `getBytes` + `update/digest`——四次 Java 调用都发生在被替换的 ArtMethod 正在执行、
栈还压在 Frida trampoline 里的时刻。现改为纯 JS SHA-256（UTF-8 编码 + 标准实现），
事件期只保留一次 `String(ret)`，**哈希语义不变**：

| 输入 | 旧实现 | 纯 JS |
|---|---|---|
| `+15551234567` | `8a59780bb8cd2ba0` | `8a59780bb8cd2ba0` |
| `中文测试` | `e350545d18735c5d` | `e350545d18735c5d` |
| `emoji😀x` | `2b5ad93b4313468b` | `2b5ad93b4313468b` |

（`empty` 不哈希、`value_len` 仍按 UTF-16 单元计，与旧行为一致；离线用
`hashlib.sha256(...).hexdigest()[:16]` 逐例比对过。）
**注意**：这属于"减少钩子体内的 Java 调用"，是风险收敛，不是已证实的解药——
args-only 组仍有 1/2 死亡。

## 4. 诚实边界（不要越界写"已修"）

1. **崩溃仍在**。10-19 白天不加改动的 4 次运行全部死亡；晚上重启模拟器后又跑了
   1 次夹具（`final-check-1`，`SIGSEGV @ Jit thread pool`）+ 3 次第三方样本（全部存活）。
   即"同一天同一台设备上，既能连续死也能连续活"——**每组 n 都是个位数，谈不了概率**，
   只能说"未消除"。本轮的修复是"后果可控"，不是"崩溃消失"。文档/答辩里应写：*插桩下
   进程仍可能被 ART 打死（上游 bridge 缺陷），已实现分段续采、覆盖率记账与死因取证，
   阴性结论按 observed_s 限定*。
2. **分段续采已在真实样本上跑通自然崩溃这一路径**（2026-10-19 复核修正）：
   - 夹具侧：`a4-smoke5` seg0 的死亡是 **JIT 线程的自然 SIGSEGV**（`pid 23666`、
     `SEGV_ACCERR @ Jit thread pool`），不是注入的 `force-stop`——本节早先写成
     "注入死亡"是**把证据读反了**（全局搜索该目录无任何 `force-stop` 痕迹）。
   - 真实样本侧：`D:/vscanner-tp/ds3-verify-vd/01-lukeneedham-videod/`（100s 窗口）
     seg0 自然崩于 `SIGSEGV @ binder:11377_4`（uptime 46s），自动 `am start` + 重新挂钩，
     seg1 存活 30.6s 并采到 **2 条 PRIVACY_READ**；账本
     `segments=2 / deaths=1 / observed_s=79.6/100 / truncated=true`。
   - 仍缺的口径：`a4-smoke5` 的 seg1 只证明"钩子重新挂上"（0 条 PRIVACY_READ），
     所以"续采"在夹具上只验证到**机制**，采到值的是上面那个真实样本。
3. 环境放大因素：模拟器 UWB HAL 每 5s abort，墓碑/崩溃缓冲被快速挤掉。
   本轮为取证临时 `setprop ctl.stop vendor.uwb_hal`，取证后已 `ctl.start` 恢复。
4. 上游依赖：frida-java-bridge #3700/#3745（x64 + API 37 的替换路径未覆盖）。
   若未来必须消除而非兜住，方向是 JVMTI MethodEntry 方案或换 arm64/较低 API 的设备，
   不是继续调 ART 参数。
