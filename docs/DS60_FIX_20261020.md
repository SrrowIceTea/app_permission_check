## 二、本轮修的六件事

### 1. UI 探索状态跨分段存活（根因）

**现象**：`device_run_thirdparty` 按 `--segment-chunk=10s` 分多次调 `explore()`，而
`tapped`/`stale`/`scrolls` 是 `explore()` 的局部变量，每次调用清零。

**证据**（`D:/vscanner-tp/ds60-sup-1019/*/ui-actions.json`）：

```
40-timer-other      : Next→Add | Next→Add | START STEP→More timer settings | （重复 5 段）
35-kerballone-spamblo: Settings→Screening | Settings→Screening | … （重复 5 段）
```

**改法**：新增 `flow.new_state()`，调用方持有一份状态跨段传入 `explore(..., state)`。
附带两处：

- 轮次号改**全局**，文件名 `ui-{r:03d}-*`。原实现每段从 `ui-00-*` 写起，**证据被覆盖**：
  `40-timer-other` 12 次点击，`ui/` 下只剩 `ui-00`/`ui-01` 两对（每段覆盖上一段）。
  注：`38-paroj-dsub2000` 不属于这一类——它的 4 组 XML 都在（`ui/`、`ui/seg1/`、
  `ui/seg2/`），只有 `ui/seg2/ui-00` 因同段两次调用被写了两次。举例子要用 40 号。
- 候选穷尽时加 **BACK 回退**（`MAX_BACKS=6`）：原来只有"往下钻"，钻进所有候选都点过
  的详情页就出不来。BACK 后若前台已不是目标包（退到桌面），立即把预算打满，避免
  "退出 → 上层 `am start` 拉回 → 再退出"的空转。

**验证**：`mobile/tools/test_ui_flow_state.py`（新增 5 例）。变异验证——把状态改回
"每次新建"，用例立刻红并复现生产形态 `['Next','Add','Next','Add']`；把恢复链改回
"直接放弃"，`stale` 用例也立刻红。

### 2. 钩子时长：只有**回退 attach** 那处真的需要余量

第一轮给主路径加了余量（spawn +55s / attach +15s）。复核后逐处核账：

| 位置 | 结论 |
|---|---|
| 主路径（spawn/attach 二选一） | 需要：窗口起点在 `wait_for_app+sleep(6)+sleep(9)` 之后 |
| **回退 attach**（spawn 失败后） | **需要**：`start_hook` 后还有 `sleep(9)` + 一次 `wait_for_app(≤20s)`，原传 `args.seconds` 至少短 9 秒 |
| 死亡重启 | **不需要**：`remaining` 在死亡时刻算，钩子还要排在 `am start+wait_for_app` 之后启动（Δ 秒），deadline 天然 = 窗口结束 + Δ |

所以只给回退 attach 加了 `+HOOK_MARGIN_ATTACH_S`；死亡重启那处保持 `int(remaining)`，
并在注释里写清为什么不加（原来我加了 15 秒，是**误判**：只是让钩子白活 15 秒）。

### 3. spawn 失败的两条路合并

`device.spawn` **超时/报错**时应用根本没被启动；原代码只在"spawn 起来的 pid 又消失"时
回退 attach，前者会直接判 `app_started` 失败并早退（40 秒等待白扔）。
而 `core/frida_host/run.py:resolve_pid` 的注释明确记着"Frida spawn 在本模拟器上会超时"。
现在 `not spawn_pid` 与 `spawn_died` 走同一个回退分支，`app_started.note` 写明回退原因，
回退会话改用 `hook-all-fallback.log`（否则 spawn 的失败原因会被 `start_hook` 的 "w" 截掉）。

### 4. 工具侧 JSONL 读取只按 LF 分行

`core/io_utils` 早已只认 LF，但工具侧还有 4 处自己写的 `splitlines()`。

**证据**：`36-ign-geoportail/session/flows.jsonl` 一条 6.7KB 记录含 **59 个 U+0085(NEL)**
（`response_payload.text` 是 latin-1 解码出的正文）。用 `splitlines()` 读，34 条记录变成
**93 段不可解析的碎片**。边界要说清：只损坏**含分隔符的那一条**，不连带后面的记录；
但本项目大量判据是"有没有 ≥1 条"，少数几条的下限就足以翻转结论。

**改法**：`core/io_utils.split_jsonl_lines()` 作为唯一出口，
`supplementary_evidence` / `fixture_selftest` / `pcap_http` / `mobile_rules_inputs` 改用它
（rules 那处原本自己写了一份 `split("\n")`，复核指出"唯一出口"当时并不成立，已改成真引用）；
`device_run_thirdparty` 的 `hook_*_armed` 判据也改走 `load_jsonl_counting`，并新增
`hook_*_jsonl_parse` 这个 optional check（有坏行就留痕，判据按下界计）；
`fixture_selftest` 原本把 `skipped` 丢掉，现在打警告。

### 5. 政策库接线（P2，只修接线，不伪造覆盖）

`batch_thirdparty.py` / `batch_dynamic.py` **在工作区里**已经支持 `--policy-store`（上一轮
加的；`git show HEAD:` 里没有，HEAD 之后的未提交改动才算），但**守护进程
`supervise_batch.py` 不转发** → 批次永远用不到准备好的本地库。已补参数与透传；
启动器只在 `catalog.json` 存在时才传（空目录会多一条误导性的 `explicit_store`）。

**但本样本集的政策一致性维度仍然不可判定**：`output/local-policy-library-fdroid`
目前 4 个样本全 `not_found`（这些 F-Droid 小工具仓库里确实没有 PRIVACY.md）。
这不是 bug，报告必须写"未取得匹配政策"，不能写"无政策"，更不能写"合规"。

### 6. 体检脚本的消费侧误读

`output/_ds60_probe.py` 的 "pids" 读的是 `conns.summary.pids`（= **留下了连接**的进程），
于是体检表把"应用没联网"写成"进程不可定位"——正是 `DIAG` 里 P1 描述的那种失真，
只不过发生在**体检脚本**这一侧。已改为 `pids_seen`，并另列"留下连接的进程"。

准确的数字（不要把两种格式混着说）：**12 个样本**有 `pids_seen` 字段，**12/12 非空**
（都读到了目标进程的命名空间）；另外 29 个是 `pids_seen` 出现之前的旧格式，只能用
`rows>0` 推断"读到过表"，无法把"读到了但没连接"和"根本没读到"分开——这正是加这个字段的
原因。所以新批次里这一列才第一次真正可判。

另外把 `conn_probe` 的并发写读加了锁——**第一次只锁了一半**：`pids_seen` 锁了，但
`write_cov()` 里还遍历 `seen`（`len(seen)`、`sorted({r["pid"] …})`），而主线程正在
`seen[key] = rec`。后果比"这一次不写"重：异常会**把心跳线程整条打死**，此后 sidecar
停在早期快照，进程又常被 kill_tree 强杀（收尾那次写不执行）。现在两个容器共用
`_state_lock`，心跳线程外面还兜了一层 try/except，收尾时先 `join` 再写最后一次
（避免两次 `write_text` 互相截断）。`rows/pid_miss` 这些 int 计数不加锁——CPython 下
读写原子，加了也只是噪音。

## 四、没有证据、所以不写进结论的话

1. **"spawn 修好了归因"**——没有实证。本机当前无设备连接，跑不了。而且 5 个真正联网的
   样本里有 3 个在 attach 模式下就拿到了 egress 事件，说明 spawn 不是唯一根因。
2. **"UI 改完就有流量了"**——只能在下一次跑批里量。而且有一个相反的风险要说清：
   状态持久化 + stale 跨段累积会让探索更早停手，必须同时看"最后一次 tap 发生在窗口第几秒"，
   否则分不清是"驱动到了联网界面"还是"提前收工"。
3. **"政策维度已恢复"**——接线通了，但库是空的，结论仍是"未取得匹配政策"。
4. **"这轮改动被验证过"**——当前代码（02:00 之后的所有改动）**一次都没有在设备上跑过**，
   全部结论来自离线单测 + 旧批次的数据分析。
