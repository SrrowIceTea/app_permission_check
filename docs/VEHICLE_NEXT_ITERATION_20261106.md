## 跨进程验收

| 场景 | 必须取得的证据 |
| --- | --- |
| A 持有读取租约，B 请求升级 | 两个不同 PID、同一 UID/用户/数据库；A 释放前 B 未完成，A 的库内容不变；释放后 B 完成 |
| A/B 同时升级同一新库 | 两进程实际重叠；一次升级、另一次无需重建；最终库与元数据一致，无 SQLite/重叠锁错误 |
| A 持锁时被终止，B 正在等待 | A 真实死亡；B 随后完成，最终库完整；不依赖 A 的 finally 释放 |
| B 等待时被终止，然后重新启动 B | A 的读取不受影响；新 B 为新 PID，能正常升级，没有残留的逻辑锁 |

每轮记录开始/持锁/释放/完成的单调时钟、进程和用户身份、原始动作与文件摘要。
最终从设备取回数据库，核对 SQLite 完整性、四表内容、schema 与生效身份。
只在临时测试用户和专用库名中执行，结束后恢复原 APK、用户并核对原用户数据库未变。

debug 工具不会进入 release；调试入口限制为系统诊断权限，并固定库名和测试路径。
单设备动态任务串行，单个源码文件不超过 300 行。失败运行保留。
