# 真实 APK 检测能力评估：问题在哪、结果是什么（2026-11-10）

> 回答三个问题：① 真实 APK 的测试结果到底是什么；② 为什么测不出来；③ 项目是不是"很 shit"。
> 全部结论来自封存产物，可复核；区分「已验证」与「未验证」。

---

## 1. 直接回答：项目不是 shit，但它确实还测不好真实 APK——原因分层

| 层面 | 判断 |
|---|---|
| **评估基础设施** | 不差。负控、完整性校验（sha256 绑定）、证据分级、跨模型盲签核——这套严谨度高于多数同阶段项目。它不会"测什么都报"，也不会把采集故障当成正常结果 |
| **对真实 APK 的检出能力** | 确实弱，但**弱的原因是结构性的，不是代码烂**：归因链在模拟器上断、数据类别覆盖窄、每个新 App 都要手写求值器。这三条下面逐条给证据 |
| **作为"商用 APK 检测产品"** | 还不是。当前架构是为受控实验评估设计的，不是为批量商店 APK 设计的 |
| **一个被忽视的事实** | **所有"测不出"的采集都做于 11-03；TLS 明文、异步批量读取、多进程 attach 是 11-10 才上的。现有真实样本数字测的是上周的能力**（已核实：6 个 case 的采集全部早于新钩子） |

所以结论是：**现在下"测不出来"的判决为时过早，但架构性的三条短板是真的，必须承认。**

## 2. 真实 APK 测试结果（全部 7 个 case）

### 2.1 逐案结果

|---|---|---|---|---|---|

| ha-control | Home Assistant | 11-03 | 2 对 WebSocket 控制（业务证据） | 不产生 finding（架构问题，见 3.1） | ⚠️ 检出但指标看不见 |

### 2.2 汇总

- 7 个 case：**3 个成功、2 个弱证据、1 个归因失败、1 个无采集**。
- 结论级判定：5 项计分中 `wrong_assertion_ratio = 0.0`（没有一次错误断言），
  但 `unobserved_ratio = 0.2`——W03 的"absent"是因为没观测，不是观测结论。
- **一个关键的架构事实：6 个 case 里 5 个的实质证据写在 `summary` 字段里，不产生 `findings`。**
  单看 `findings_total` 会认为"几乎全零"，实际是「检出存在但指标看不见」。

## 3. 为什么测不出来：五个结构性原因（按重要性排序）

### 3.1 检出结果与指标口径脱节（架构性，修起来最容易）

`vehicle/privacy/pipeline.py::append_general` 只有 `ha_webhook` 和 `owntracks_location`
会 `records.extend(...)` 产生 finding；`ha_socket`、`mg4`、`abs` 三个专用求值器
**只往 summary 写字段**。于是"有没有检出"取决于你读哪个字段——这就是"感觉测不出来"的
直接来源。已通过 `detection_summary.py` 分列（规则命中/业务证据/零观测），
但**指标口径本身还没统一**。

### 3.2 采集→归因→正文链在模拟器上断裂（硬件性，模拟器无解）

模拟器 SLIRP NAT 不保留源端口，`/proc/net/tcp` 轮询抓不到几十毫秒的连接：
- `mg4-post`：11 条流全部 `outside_allowlist_or_unresolved` 被丢弃，代理明明看见了 POST；
- `mg4-webview-post`：只能用"App 侧事件 + 服务端同值正文"的替代关系，**代理逐流身份未核验**。
这条线在模拟器上**结构性无解**，需要真实设备。

### 3.3 数据类别与规则覆盖窄（工作量问题，不是原理问题）

- 通用求值器只支持 `android_id / contacts / location / microphone / advertising_id`——
  **没有电量**。金标准确认的 HA 电量外发，通用路径 recall = 0.0；
- `location` 有读取但**没有外发关联**（`evaluation.py` 只做读取匹配）——定位外发是已知未闭环；
- 规则库 13/16 版的 `data_egress` 规则全部 `enabled=0`，原因写明"未做外发窗口标定"——
  这是项目自己的克制，但也意味着可用规则少。

### 3.4 每个新 App 需要手写契约求值器（规模化瓶颈）

HA 有 `ha_evaluation`，MG4 有 `mg4_contract`+`mg4_write_evidence`，YAABSA 有 `abs_runtime`。
每个 App 一个专用求值器 + 契约哈希绑定。**这个架构扩不到"批量商用 APK"**——
通用路径才是可扩展的那条，但它目前类别少、外发关联只覆盖 2/5 类别。
这是"商用检测产品"与"实验评估系统"的本质差距。

### 3.5 ⚠️ 测量时点错位：现有数字测的是上周的能力（可行动）

已核实（`reads.jsonl` 时间戳与钩子装载记录）：

| 采集增强 | 上线时间 | 6 个真实 case 的采集里有没有 |
|---|---|---|
| TLS 明文（`SSL_write@libjavacrypto.so` + 12 个 Cipher 重载） | **11-10** | 无 |
| 异步/批量 VHAL 读取（按设备实测签名） | **11-10** | 无 |
| 多进程 attach | **11-10** | 无 |

即：**真实样本的"测不出来"，是在没有这三项能力的采集上测的。**
用新 bundle 重采同样的 3 个 App，是当前**唯一可能直接改变数字**的动作，且成本最低。

### 3.6 另一个必须说清的事实：样本是"真实"但不是"商用闭源"

当前 4 个样本都是**开源 AAOS 应用**（HA、MG4 浏览器、YAABSA、AudioWagon）。
真正的商业 APK（闭源、混淆加固、证书绑定、Play Integrity）难度更高：
加固壳会挡 Frida、证书绑定需要绕过（项目有 `ssl_pinning_bypass` 但未在商业样本上验证）、
多进程+多架构（64/32 位）会让 attach 覆盖更碎。**当前结论不能外推到"商用闭源 APK 可检测"。**

## 4. 什么不是问题（对冲判断，防止矫枉过正）

- **负控行为全部正确**：read-only、different-value、503 失败，全部零误报——系统不是"乱报"；
- **无错误断言**：真实样本上 `wrong_assertion_ratio = 0.0`；
- **完整性链条严格**：契约哈希绑定、参考证据 sha256 校验、32/32 匹配——
  曾经的"数字可复现是运气"已变成"有校验的复现"；
- **AI 与评分没有越界**：证据能力字段 + 分句否定校验后，"只有属性名命中却写已传输"会被拦截。

换句话说：**系统没有"测不出来"的病，它有"看得见的少"和"够不着的链"。**

## 5. 现在能做什么（按 ROI 排序）

| 序 | 动作 | 预期 | 成本 |
|---|---|---|---|
| 1 | **用新 bundle 重采 3 个真实 App**（HA/MG4/YAABSA，场景同上） | 直接检验 TLS 明文/异步读取对真实流量的增量；可能改变 mg4 的证据等级 | 一次采集轮，设备在线即可 |
| 2 | **统一指标口径**：让 ha_socket/mg4/abs 的业务证据也产生 finding（带证据等级标记） | `findings_total` 不再系统性低估；这是修"感觉测不出来"最直接的一刀 | 纯代码，中 |
| 3 | **通用求值器补 location 外发关联** | 闭环已知缺口；但必须有真实样本验证才算数 | 纯代码，中 |
| 4 | **真机** | 一次解决 SLIRP 归因 + USB 介质两个硬件阻塞 | 需要硬件 |
| 5 | 规则库窗口标定，启用 13/16 的 data_egress 规则 | 可用规则翻倍 | 需要标注/标定数据 |

不建议：为了数字好看去实现无标定依据的类别（battery 之所以没做就是这个原因）；
强行绕过授权范围（设备上的系统应用）。

## 6. 一句话总结

**评估基础设施是认真的，检出能力在真实 APK 上目前是弱的——但"弱"的三个主因里，
一个是指标口径（可修）、一个是测量时点（可重测）、一个是硬件（需真机）。
在下一次用新 bundle 重采真实 App 之前，"测不出来"这个判决证据不足。**
