## 三、spawn 的结论：这台模拟器上不可用（3/3）

三次都在 `device.spawn` → `resume` 后的 6 秒观察窗内失去 pid：

```
01  spawn pid=5959  已消失 → 回退 attach pid=6393
02  spawn pid=12532 已消失 → 回退 attach pid=13015
03  spawn pid=18904 已消失 → 回退 attach pid=19055
```

这与 `mobile/DECISIONS.md` 里 `exp_spawn_keylog.py` 记的旧结论一致（"钩子全 ARMED 后 pid 第 5s
消失，重启的新 pid 没有任何钩子"），也解释了为什么 `core/frida_host/run.py:resolve_pid` 的报错
文案写着 spawn 会超时。

**代价**：每个样本多花 `wait_for_app(≤40s) + 6s` 才回退；01 还因此多出一次死亡
（`app-death-seg0`：`SIGABRT ... DefaultDispatch`），使该样本 `covered=false`、阴性结论只能
限定在 85.1s 内。

**决定：启动器默认不再开 `--spawn-hook`**（`SPAWN=1` 可显式打开）。
原因不是"spawn 代码有问题"，而是**这台 AVD 上它必然失败**：失败一次就是 40 秒 + 一次死亡记录。
「首启流量漏采」这个真问题仍然存在，但在 spawn 不可用的环境下，pcap 才是首启流量的主证据。

## 四、这一轮**没有**解决、且被本次运行再次证实的

1. **keylog 仍然是 0 行**：02 的 `http-stats.json` 写着 `keylog_lines=0`、`tls_encrypted_without_body=411`、
   `bodies=0`。pcap 里 43 条报文全是**未解密的明文部分**，明文 body 一条都没有。
   这正是 `PLAN_OPTIMIZATION_20261020.md` 里 P0-1③ 的老问题，**本轮没碰**。
2. **"有事件"≠"每条流都有事件"**：01 有 16 条 flow 但只有 1 条 `EGRESS_URL`；02 有 38 条 flow / 18 条
   `EGRESS_CONNECT`。钩子挂在 connect/URL 构造层，keep-alive 复用连接时零事件——这条限制没变。
3. **批前夹具自检仍是 degraded**：`有效观测 50.7/100s`，夹具进程在窗口内死于
   `SIGSEGV@Jit thread pool`（A1 残留）。批次默认放行并标注，但"窗口完整性"不成立。
4. **政策**：`policy_from_apk` 返回 3（APK 内不含政策页），本地库仍然为空 → 三个样本的
   政策一致性维度依旧不可判定。

## 五、复现方式

```bash

  --apk-dir D:/vscanner-tp/apk3 --out D:/vscanner-tp/verify-1021 \
  --static-reuse "D:/数据集/数据集/static-batch-fdroid60" \
```

`%USERPROFILE%\.android\avd` 拼路径，而本机 AVD 在 `ANDROID_AVD_HOME=D:\Android studio\AVD`，
